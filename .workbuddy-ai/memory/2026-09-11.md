## 从零搭建 ai-workbench 桌面应用仓库

**目标**：Electron + React + TypeScript + Vite 的 monorepo 桌面应用骨架（最小可运行）。

**最终结构**（工作区根目录 `C:\Users\bing\workbuddy-ai\work123`）：

```
apps/desktop   前端 + Electron（vite.config.ts / electron/main.ts / electron/preload.ts / src/）
apps/server    空占位，只有 README
packages/shared 共享 TS 类型（ChatMessage / ChatSession / WorkbenchBridge）
scripts/clean.mjs
```

**关键技术决策**：

1. **包管理器用 npm workspaces，不用 pnpm** —— pnpm 在本机的依赖链接会退化成空目录，
   完全无法解析依赖。详见用户级 `~/.workbuddy-ai/MEMORY.md`。
2. **主进程/preload 单独用 `tsc -p tsconfig.electron.json` 编译成 CommonJS**（输出 `dist-electron/`），
   渲染进程交给 Vite。不用 vite-plugin-electron，结构更透明。
3. **一条命令启动**：`concurrently` + `wait-on tcp:5173` + `cross-env VITE_DEV_SERVER_URL=...`。
   main.ts 靠 `VITE_DEV_SERVER_URL` 是否存在来区分 dev / 生产，而不是 `app.isPackaged`
   （`electron .` 未打包时 `isPackaged` 也是 false，会误判）。
4. **启动包装器** `apps/desktop/scripts/start-electron.mjs`：先按安全参数启动，
   捕获 `GPU process isn't usable`（退出码 2147483651）后自动加 `--no-sandbox` 重试一次。
   原因见用户级 MEMORY。
5. 安全设置：`contextIsolation: true` / `nodeIntegration: false` / `sandbox: true` +
   preload 白名单 `window.workbench`。已实测渲染进程拿不到 `require` / `process` / `ipcRenderer`。

**已验证**（端到端跑通）：
- `npm run typecheck` / `npm run build` 全绿
- `npm run dev` 一条命令起 Vite + Electron，窗口打开，标题「AI 工作台」
- 渲染进程 `window.workbench.ping()` 返回 `pong from electron 33.4.11`，IPC 链路通

**已知缺口**：
- 生产环境 CSP 未加（避免打断 Vite HMR）；Electron 在 dev 下会打印一条 CSP 提示，打包后消失。
- `apps/server` 还是空的，加代码时需要补 `package.json` 才会被 npm workspaces 识别。

## 第 1 步验收（同日）

验收标准：`npm run dev` 弹出桌面窗口，窗口里能看到 React 的「AI 工作台」。

用临时探针从真实渲染进程读回 DOM 取证（验完已删除），关键结果：

```json
{"windowVisible":true,"windowTitle":"AI 工作台","url":"http://localhost:5173/",
 "documentTitle":"AI 工作台","heading":"AI 工作台","brand":"AI 工作台",
 "bridge":"object","leakedRequire":false,"leakedProcess":false}
```

`url` 是 dev server 而非 `dist` 旧产物，说明确实走的 Vite HMR 链路。

**验收中发现并修掉的两个真实缺陷**（都在 `apps/desktop/package.json` 的 dev 脚本）：

1. **关掉窗口会报成失败**。Electron 正常退出 code 0 → `concurrently -k` 连坐杀掉 vite →
   vite 退出码 1 → concurrently 默认 `--success all` 判定整体失败 → 终端刷一片 `npm error`。
   修复：加 `--success command-electron`，整体退出码跟随 Electron。
   实测 `npm error` 从 3 行降到 0 行。

2. **vite 起不来时 `wait-on` 会永久挂住**（strictPort 下端口被占，vite 直接退出，
   而 wait-on 默认 timeout 是 Infinity）。修复：`wait-on tcp:5173 -t 30000`。

**环境注意**：Windows 下 `concurrently` 杀的是 `cmd.exe` 包装进程，孙进程 vite（node.exe）
可能存活并继续占着 5173，导致下次 `npm run dev` 报 "Port 5173 is already in use"。
反复非交互式启停（自动化测试）容易攒下孤儿进程；手动 Ctrl+C 一般正常。
清理方式见用户级 `~/.workbuddy-ai/MEMORY.md` 的 taskkill 条目。

## 「神秘失败」排查（同日，重要）

验收过程中多次出现后台任务报 `failed`，一度怀疑是代码缺陷。最终查明**全部是我自己反复启停
留下的孤儿实例造成的**，与产品代码无关。

**症状签名**（很迷惑，容易误判）：

```
[vite] Error: Port 5173 is already in use      ← 新实例的 vite 绑不上
[electron] [launch] Electron 已退出：code=0 signal=无，运行 1s   ← 撞上单实例锁
[electron] wait-on ... exited with code 1      ← 但 wait-on 却成功了
```

关键矛盾点：`wait-on tcp:5173` **成功**了，因为**旧实例的 vite 还在监听 5173**；
而新 Electron 因为 `app.requestSingleInstanceLock()` 拿到 false，1 秒内静默退出、退出码 0。
两者叠加就产生了"端口被占 + electron 秒退 + 整体失败"的诡异组合。

**根因**：`npm → cmd.exe → concurrently → (vite / 启动包装器)` 是一条进程链，
`TaskStop` 或单点 taskkill 只能带走一部分，残留实例继续占着 5173 和单实例锁。

**可靠清理方式**（只杀端口监听者不够）：

```bash
taskkill /F /IM electron.exe /T
PID=$(netstat -ano | grep ":5173.*LISTENING" | awk '{print $NF}' | head -1)
[ -n "$PID" ] && taskkill /F /T /PID "$PID"
sleep 10   # 复查：若 electron / 端口又冒出来，说明还有实例，继续杀
```

**顺带加的两个诊断**（都是这次调试倒逼出来的，有实际价值）：
1. `start-electron.mjs` 退出时打印 `code / signal / 运行时长` —— 正是它一句话锁定了"1 秒退出 code=0"。
2. `main.ts` 单实例锁失败时打印 `[main] 检测到已有实例在运行…` —— 否则新进程静默退出，极难排查。

## 第 2 步改版：独立窗口 → 主窗口内嵌 webview（同日，推翻上一版）

**需求变更**：不再弹独立 BrowserWindow，改成主窗口右栏内嵌 `<webview partition="persist:workbench-browser">`
直接显示真实网页；`暂停/继续/我来操作` 除了改文案，还要控制这块区域能不能点。

**改动**：主窗口 webPreferences 加 `webviewTag: true`；删掉整个独立窗口模块；
4 条 IPC 改成「渲染进程 → 主进程 → `mainWindow.webContents.send` 转发回渲染层」；
preload 加 `openBrowser(url?)` / `showBrowser` / `hideBrowser` / `focusBrowser` / `on(event, cb)`；
`global.d.ts` 补 `JSX.IntrinsicElements.webview`；App.tsx 右栏 = 文案 + 控制 + 任务卡 + 内嵌浏览器区。

**⭐ 本步最值钱的坑：`<webview>` 的 `display` 不能写成 `block`。**

症状：元素 `getBoundingClientRect()` 是 581×489，但网页只画在上面 150px 高的一条里，右边挂滚动条。
先怀疑是 PrintWindow 截不到 OOPIF，换整屏截图对照 → 确认是**真实渲染问题**。

实测对照（同一元素，只改 CSS）：

| 写法 | 元素高 | guest 视口高 |
| --- | --- | --- |
| `display: block` | 489 | **150** ❌ |
| `display: flex` | 489 | **489** ✅ |
| `display: inline-flex` | 489 | **489** ✅ |
| `display:block` + 内联 `height:489px` | 489 | **150** ❌ |
| `display:block` + 尺寸 nudge | 489 | **150** ❌ |

结论：`<webview>` 内部靠 flex 撑开 guest，`block` 会让它退化成默认 150px，给死高度也救不回来。
写法固定为：CSS 里**不写 display**，内联 `style={{ display: visible ? 'flex' : 'none' }}`。

**另一个坑：`webContents.sendInputEvent` 注入到主窗口不会穿透到 OOPIF guest。**
想用它验证 `pointer-events: none` 时，AI 态和用户态都是 0 次点击，看起来像「挡住了」，其实是压根没送达。
改用 `document.elementFromPoint(webview 中心)` 做 A/B —— 它走的就是 Chromium 的命中测试：
AI 态返回容器 `div`（跳过 webview），用户态返回 `webview`（命中）。另外先往 guest 塞合成点击把计数器校准到 1，
证明「量具」有效，否则 0 和 0 无法区分。

**第三个坑：真实鼠标点击在这台机器上时灵时不灵。**
红点按钮点 5 次全落空，但同一坐标早先点成功过一次；`打开工作台浏览器` 也是扫了 9 个坐标才命中一个。
稳定套路：① `SetWindowPos(HWND_TOPMOST)` + ALT 解锁 + `SetForegroundWindow`；② **先点一下标题栏真正激活窗口**；
③ 鼠标不可靠时改用键盘（`Shift+Tab` 回到第一个可聚焦元素 + `Space` 激活，实测一次成功）。

**产出**：`docs/acceptance/step-2-main-window.png`（一张图同时含红点、手打消息、右栏 example.com）、
`docs/acceptance/step-2-prod-main-window.png`（生产模式）、`docs/acceptance/step-2-验收报告.md`。
旧的 `step-2-two-windows.png` / `step-2-workbench-browser.png` 已删除。

**额外补验了生产模式**（`npm run start`，走 `loadFile` 而不是 dev server）：
内嵌 webview 同样正常，左下角 `桥：win32 · pong from electron 33.4.11` 证明 preload + IPC 在生产下也通。
结论：dev 与 prod 两条路径都验过了。

**⚠️ 新坑：键盘 Tab 会跑进 webview 里。**
验证生产模式时我用 `Tab + Enter` 循环找按钮，结果焦点进到 webview 内部的链接上，
回车把 example.com 点成了 IANA 的 Example Domains 页，同时「暂停」被触发（文案变成"你正在控制"）。
用键盘驱动内嵌 webview 的应用时，要注意 Tab 顺序会跨进 guest 页面，别把它当成"按钮没反应"。
另外：点标题栏激活窗口时坐标别选正中间，窗口被最小化过（x=-32000），操作前先 `ShowWindow(SW_RESTORE)`。

## 第 3 步「遥控器先通」：驾驶内嵌 webview（同日）

**目标**：让程序能驾驶主窗口右栏那块内嵌 `<webview>`（打开网址 / 点击 / 输入 / 滚动 / 读页面 / 暂停）。
不接大模型（`ask_user` / `done` 只定类型）、不登录、不做后端、不重做 UI、不弹独立窗口。

**改动（6 个文件）**：

- `packages/shared/src/index.ts`：新增 `BrowserAction`（含 `read_page` / `screenshot` 扩展）、
  `PageSnapshot`、`DriveResult`（含 `detail`）；`WorkbenchBridge` 加 `drive` / `readPage` /
  `pauseDriving` / `resumeDriving`
- `apps/desktop/electron/driver.ts`（**新增**）：CDP 执行器。目标 = guest `webContents`，
  `debugger.attach('1.3')` + `Runtime.evaluate` / `Input.dispatchMouseEvent` / `Page.captureScreenshot`
- `apps/desktop/electron/main.ts`：3 条 IPC（`workbench:drive` / `read-page` / `pause-driving`）
- `apps/desktop/electron/preload.ts`：白名单加 4 个方法
- `apps/desktop/src/App.tsx`：右栏加 8 个按钮的调试区（丑是故意的）+ 结果显示
- `apps/desktop/src/styles.css`：调试区样式

**架构决策**：主进程拿 guest webContents 再挂 CDP，而不是在渲染层用 `webview.executeJavaScript`。
理由：CDP 能拿到真实鼠标事件、截图、命中测试；渲染层也就不用碰任何 Electron 能力（`contextIsolation` 不动）。

**⭐ 本步最值钱的三个坑（都会"静默失败"，回执看着是成功的）**：

1. **CDP 文本注入完全不生效**。实测 7 种方式：`Input.insertText`、逐字符 `Input.dispatchKeyEvent`、
   `DOM.focus + insertText`、`Page.bringToFront` 全部**不报错但值仍为空**；只有
   `document.execCommand('insertText')` 和「原生 setter + `InputEvent`」有效。
   → `type` 做成三层兜底 + **每次写回后读回 `el.value` 校验**，并把生效方式写进 `detail`。
   （**鼠标事件不受影响**，`Input.dispatchMouseEvent` 正常。）
2. **点击坐标在视口外 → 静默失败但回 ok:true**。内嵌页视口只有约 **551px** 宽（右栏 50vw），
   百度首页那排搜索 UI 固定 **771px** 宽，把「百度一下」挤到视口右边外面。
   → 先用 `elementFromPoint(中心)` 做命中测试；命不中退化为页面侧 `el.click()`，并在 `detail` 说明。
3. **`querySelector` 会选中不可见的元素**。百度首页隐藏的经典 `#kw`/`#su`（祖先 `display:none`，
   自身 computed display 仍是 `inline-block`，只有 `getBoundingClientRect()` 量出 0×0）
   排在可见的新版搜索框 `#chat-textarea` / `#chat-submit-button` **前面**。

## 第 3 步 P0 修复：暂停后内嵌页不能点（同日）

**根因 1（主因）**：`apps/desktop/src/App.tsx` 曾按 `controller === 'ai'` 给 `<webview>`
写 `pointer-events:none`。这会让 Chromium 主窗口命中测试直接跳过 guest，页面视觉存在但用户点不到。
修复为 webview **始终 `pointer-events:auto`**；暂停语义只由主进程执行器的 `paused` 开关拦截自动
`click/type`，不再用 CSS 锁用户输入。

**根因 2（百度结果链接）**：很多百度结果带 `target=_blank`。webview 不带 `allowpopups` 时，用户手点
看起来无反应；若真新开 BrowserWindow 又违反产品约束。修复：webview 加 `allowpopups`（布尔属性），
主进程 `app.on('web-contents-created')` 对 `webview` guest 设置 `setWindowOpenHandler`，统一 `deny`
新窗口并 `contents.loadURL(url)` 到**当前 guest**。实测 target=_blank 的百度结果会在右栏当前页跳转，
`BrowserWindow.getAllWindows().length` 始终为 1。

**验收**：以 `npm run dev` 真窗口跑两轮临时探针（验后已删）。每轮：A 驾驶打开百度/输入/搜索/读页；
B 暂停后 CSS 命中返回 WEBVIEW、自动 click 被拒绝、guest 真鼠标/键盘输入获得 `chat-textarea` 焦点且
value=`human-P0`、滚动 `scrollY 0→960`、手点百度 `target=_blank` 结果跳当前 guest；C example.com
手点 Learn more 跳 IANA；D “我来操作”、继续→暂停、窗口缩放后手点仍都跳。P0 报告：
