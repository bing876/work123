### 二、根因（对 `app.asar` 取证得到）

- 客户端逻辑：`folder = process.env.WORKBUDDY_DATA_FOLDER_NAME?.trim() || ".workbuddy"`
  → 工作区记忆目录 = `${cwd}/${folder}/memory/`。
- `WORKBUDDY_DATA_FOLDER_NAME` 由 `configureElectronApp` 冷启动写入，值来自
  `product.json#dataFolderName`（本机实测 **`".workbuddy"`**；海外版才是 `.workbuddy-ai`）。
- 而本仓库**跟踪的目录**是 `.workbuddy-ai/memory/`（**首个提交 `dc335d6`** 建立）。
- → **不是仓库里有哪处配置写错了，是平台的产品级常量与仓库跟踪路径不同名。**
  `dataFolderName` 由 `apply-brand-patch.js` 在产品构建期写入，**改它等于换掉整个客户端的配置目录**
  （`~/.workbuddy` 也会跟着变）→ 风险远大于收益，**不碰它，改仓库**。

### 三、最终修法：目录名直接对齐（联接方案当日否决）

- 先按"最小改动"试了 **Windows 目录联接（junction）**：`<repo>/.workbuddy/memory` →
  `<repo>/.workbuddy-ai/memory`，写入穿透已验证（两路径 inode 相同）。**同日否决**，理由见上。
- 改为 **一次性 `git mv` 改名**：`git mv .workbuddy-ai/memory .workbuddy/memory`
  → 跟踪路径 = 平台默认路径，`git status` 识别为 **`R100`**（未改动文件 100% 相似）。
- 配套清理：
  - **撤销目录联接**：用 `os.rmdir`（Windows 上是 `RemoveDirectoryW`）摘掉重解析点 ——
    **只删联接本身**，目标目录 10 个文件完好无损；再删掉空的外层 `.workbuddy-ai/`；
  - **删除** `scripts/link-memory-dir.mjs`（不再需要）；
  - **撤掉** `.gitignore` 里刚加的 `.workbuddy/` 规则（它现在是正式跟踪目录，必须能被 git 看见）。
- 净效果：**不需要任何联接、脚本或平台特有技巧；`.gitignore` 零规则；克隆到新机器天然一致。**

### 四、踩到的坑：`.workbuddy-ai` 目录**本身**被占用（EPERM）

- `git mv .workbuddy-ai .workbuddy` 直接失败：
  `fatal: renaming '.workbuddy-ai' failed: Permission denied`；node `os.rename` 同样 `EPERM`。
- 用"逐层试改名"定位（比猜进程快得多）：

  | 试什么 | 结果 |
  |---|---|
  | 外层目录 `.workbuddy-ai` 改名 | ❌ EPERM |
  | 内层目录 `.workbuddy-ai/memory` 改名 | ✅ OK |
  | 目录内单个文件改名 | ✅ OK |
  | 仓库根新建 `.workbuddy/` | ✅ OK |

- 结论：**只有外层那个目录本身被某个进程持有句柄**，内容完全不受影响。
- 绕法：**先搬内容、再删空壳** —— `git mv .workbuddy-ai/memory .workbuddy/memory`
  之后外层变空，`os.rmdir` **立刻成功**。
- 另一条 `git mv` 细节：目标若**已存在同名目录**，语义是"移动**进去**"（POSIX `mv` 语义，
  会变成 `.workbuddy/memory/memory`）—— 所以目标路径要先确认不存在，或直接拼到最终文件名。
