## 2. 数据结构变更

```sql
-- 当前使用中的项目；为空时回落到 is_default 那条（老账号行为一行不变）
ALTER TABLE users              ADD COLUMN IF NOT EXISTS current_project_id BIGINT REFERENCES projects(id) ON DELETE SET NULL;
-- 权限开关：能不能建智能体。母鸡/自带小助 true；用户自建智能体默认 false
ALTER TABLE agents             ADD COLUMN IF NOT EXISTS can_create_agents BOOLEAN NOT NULL DEFAULT false;
-- 知识库项目归属（老数据由 migrateProjectScope 按 owner 各自回填到默认项目）
ALTER TABLE knowledge_documents ADD COLUMN IF NOT EXISTS project_id BIGINT REFERENCES projects(id) ON DELETE CASCADE;
ALTER TABLE knowledge_chunks    ADD COLUMN IF NOT EXISTS project_id BIGINT REFERENCES projects(id) ON DELETE CASCADE;
-- 两个索引 + 回填确认无空值后把 project_id 收紧为 NOT NULL
```

`projects` / `agents.project_id` / `conversations.project_id` / `tasks.project_id` / `memories.project_id`
**本来就存在**（第 5 步建的），本次没有重建、没有改外键。

**两处不变量**（`db.ts` 的 `migrateProjectScope()`，每次启动幂等执行，只补空值）：

1. `users.current_project_id` 为空 → 取该用户 `is_default` 那条（老账号 = 什么都没发生）。
2. `kind IN ('assistant','hen')` 的行权限必须为 true → 老库补上，老账号照样能点「＋ 添加」。
3. 知识库 `project_id` 为空 → 按 **owner** 各自挂到自己的默认项目（不是一刀切挂到某一个项目）。

## 3. 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/projects` | 我的项目列表，标出 `isCurrent`；每条带 `henAgentId` |
| POST | `/projects` `{name}` | 建项目 → **同一事务里连带建一只母鸡**（`kind='hen'`、`can_create_agents=true`、`persona_status='ready'`、含一条空会话）→ 设为当前项目 |
| PATCH | `/projects/:id` `{name}` | 重命名（≤24 字，空白折叠） |
| POST | `/projects/:id/activate` | 设为「当前使用中的项目」 |
| GET | `/agents?projectId=` | 可选按项目过滤；不传 = **改造前的行为**（账号全部智能体） |
| POST | `/agents` `{asAgentId}` | 建智能体前**校验调用者权限**（`asAgentId` **必填**，不传/非法 400）；新人落在**调用者所在的项目** |
| GET | `/knowledge?projectId=` | 项目隔离；不传 = 当前项目 |

三条统一口径：归属一律来自 JWT 的 `claims.sub`（不接受客户端传 owner）；
不是自己的项目/资料一律 **404**（不区分「不存在」与「是别人的」，避免用 id 探测）；
内置角色（小助 / 母鸡）**不可删**、**有建智能体权限**。

后端权威闸 + 前端两条入口都盖住了，并且做了**正对照**（不是「一律拒删」）：

PASS  母鸡被拒删后**数据库里那行仍在**（不只是回了个错误码） :: agents(id=49) 命中 1 行

PASS  前端那条**唯一没按 deletable 判**的删除入口也进不去：母鸡 personaStatus 恒为 ready → 引导表（内含删除按钮）永不渲染

PASS  正对照：普通智能体删得掉（DELETE 200 + 库里那行没了）—— 闸门只挡内置角色 :: status=200 剩余行=0
PASS  母鸡在整轮测试跑完后依然在（从头到尾没被删掉过）

**前端为什么不用改也拦住了**（两条路，都核对过 `App.tsx`）：

- `App.tsx:1641` 的「删掉「X」」按钮：条件是 `curAgent.deletable` → 母鸡 `deletable=false`，按钮根本不渲染（grep 确认这是唯一的列表删除入口）。

## 8. 本轮抓出并修掉的 2 个真 bug（别再踩）

### bug #1 —— **服务运行期间新注册的账号，小助没有建智能体的权限**

`auth.ts` 建号时插小助那句 `INSERT INTO agents (project_id, name, kind)` **没带 `can_create_agents`**，
列的默认值是 `false` → 新账号一点「＋ 添加」直接 403。
原来那套「启动时不变量回填」只在**重启时**跑，**盖不住运行期间新建的行**。

- 触发方式：起后端 → 用新手机号注册 → `POST /agents` → 403（就是本轮接口验收第一条 FAIL）。
- 修法：建号那句**显式写 `can_create_agents = true`**（母鸡的建法本来就是显式的，两边对齐）。
- 教训：**列的默认值是给「用户自建智能体」的**；内置角色必须在每一个插入点显式给值。

### bug #2 —— **前端有一条删除入口绕过了 `deletable`**

`App.tsx:1900` 的 `<AgentGuide onDelete>` **没有**按 `deletable` 判，只在 `personaStatus === 'pending'` 时渲染。
本阶段不允许改前端，所以从后端把这条路的触发条件消掉：`toAgentView()` 对内置角色（小助 / 母鸡）
**一律返回 `personaStatus: 'ready'`** → 引导表永不为它们渲染 → 那条无守卫的删除入口**结构性不可达**，
后端 `DELETE` 仍是权威闸（400）。

## 9. 已知限制 / 需要总控确认的取舍点

1. ~~**`POST /agents` 不带 `asAgentId` 时回落到「自带小助」**~~
   → **总控已拍板（§12）：改为必填，不传/非法直接 400，不允许回落到任何身份。**
   指令原话的风险判断：默认回落到母鸡/小助这种**有权限的内置角色**，等于「不传身份的调用绕过权限校验拿到最高权限」，
   这个风险不能带着走。
2. ~~**新智能体落在「当前使用中的项目」，不是「调用者所在项目」**~~
   → **总控已拍板（§12）：改为「调用者（母鸡）自己所在的项目」。**
   理由：用户在界面上切换项目视角，不该把新智能体塞进别的项目；「一个智能体只属于一个项目」这条边界要保持干净。
3. **知识库检索按「会话所属项目」过滤**，不再按账号。
   直接后果：一份挂在项目 B 的资料，在项目 A 的会话里**检索不到**（这正是「按项目隔离」的语义）。
   老会话都在默认项目里 → 对老用户无感。
4. **项目不可删除**（本阶段边界），`is_default` 那条永远保留兜底。
5. `/projects` 列表 `LIMIT 50`；项目名 ≤ 24 字。
6. `session.project` / `AgentView.projectId` 已经下发，但**前端一次都没读**（2-A 不动前端）。

### 12.3 本轮抓出并修掉的第 3 个真 bug（在**取证脚本**里，最阴的那种）

**`2a-migrate-replay.mjs` 把迁移基线写死成 `HEAD`。**

- 它在 2-A **还没提交**的时候跑，`git show HEAD:db.ts` 恰好是「加新列之前」的 DDL → **碰巧正确**，
  首轮 12 条全 PASS。
- 但 2-A 一提交进历史，`HEAD` 就变成**加新列之后**了 → 验收库里那个「迁移前」结构**自带新列**，
  整条对照退化成「迁移后 vs 迁移后」，**其余 11 条照样全 PASS** ——
  只有那条「新列都不存在」的断言在报警。这次复跑正是靠它才发现（`FAIL` 一条）。
- 修法：不写死，从 HEAD 往回找第一个 `db.ts` 里不含 `can_create_agents` / `current_project_id` 的提交，
  并把选中的 sha 写进证据 JSON；`MIGRATE_BASE_COMMIT` 可人工覆盖。
- 教训：**「验收脚本自己」也会腐化，而且腐化时往往表现为「依然全绿」**。
  凡是从 git 取基线的东西，都要断言「取到的确实是那一版」（这次就是靠这条断言兜住的）。

顺带修掉一个**会让证据不可复现**的小问题：内容摘要原先把 `created_at` 也算进去，
那是「往一次性验收库里插入的时刻」，每轮都不同 → 同一个库、相同内容，摘要却每轮变，
报告里那个「前后一致」的 sha 没法跨轮比对。现在内容指纹**不含写入时刻**（跨轮稳定），
另外单加一条 `id + created_at` 指纹做**同轮内**对比，证明迁移是「原地加列、没重写行」。
